READING
  * G4-13 puts REGISTRY.digest() in every match's input hash; G6-11 registers
    the three functions in REGISTRY. So the digest changes (7ddf4747… ->
    47188d01…), and the first run after step 3, on UNCHANGED facts, does not
    find an identical input: it stores a NEW match (run 2). From then on the
    new match is reused as before (run 3).
  * The old match is not changed and stays verifiable: it records 7ddf4747…,
    which registry_history.HISTORY[0] holds.
  * Consequence for the queues (Slice 5, G5-2, derived, not measured here):
    the new match is a later match of the same request, property, policy and
    offer, so it supersedes the old one for an approval and in the match queue.
    This is G4-2's designed behaviour for any new registered version; step 3
    is the first time it happens in this repository.
  * Step 3's run calls none of the three functions; this change comes from
    their registration alone.
