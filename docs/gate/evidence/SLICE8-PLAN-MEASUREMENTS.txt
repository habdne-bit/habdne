Reading (what each measurement shows, and no more):
- M1: the application writes external_leads by one INSERT only. No path moves a
  status. The suite's database holds one DECLINED lead: written by a TEST, by SQL
  (tests/test_slice3_sources.py, the queue test), not by the application.
- M2: the partial unique index serializes two concurrent ACTIVE interests: the
  second waits for the first's commit, then fails 23505 on
  ux_active_interest_per_pair. One ACTIVE row.
- M3: the binding trigger accepts the request's party's ASSISTED_ENTRY grant, and
  refuses another party's, a revoked one, and a purpose other than the grant's
  scope. G8-5 (i)'s assumption holds at the moment of writing.
- M4: the trigger reads the grant WITHOUT a lock, and the foreign key takes only
  FOR KEY SHARE, which does not conflict with the revocation's UPDATE of a
  non-key column. So (a) and (b): the revocation commits FIRST, and the
  conversion still commits a binding to a grant revoked before its commit.
  (c) FOR SHARE on the grant, before binding: the revocation waits, and commits
  after the conversion: the binding was valid at the conversion's commit, and is
  made inert by the later revocation (ADR-04). (d) The revocation first,
  uncommitted: the conversion's FOR SHARE waits, then finds no GRANTED grant, and
  the service refuses. So the conversion must take FOR SHARE (or stronger) on the
  grant, re-check it is GRANTED and unrevoked, then bind, in one transaction.
- M5: before any new constraint, no lead in any database here carries a
  workflow column; the only non-DISCOVERED lead is the test's DECLINED one; no
  ACTIVE interest pair is held twice; no reason code is named LEAD_*; no table
  external_lead_contact_attempts exists. These are this server's test and probe
  databases: no evidence about any deployed database.
- M6: keyset paging on (discovered_at, external_lead_id) skips a lead whose
  inserting transaction began before the cursor's row and committed after the
  page was read: discovered_at is now(), the transaction's start, so the late
  commit sorts before the cursor. Any cursor on an insert-time column has this
  gap; commit order is not timestamp order.
