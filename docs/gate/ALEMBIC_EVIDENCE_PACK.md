## 2. R14.4–R14.7, verbatim

From `docs/rfc/RFC-001-object-level-authorization.md` §14.2, *"Alembic must
not redefine the frozen baseline"*:

> Alembic autogeneration compares models to a live database and emits a
> migration. Pointed at the frozen schema it will happily produce a diff that
> quietly becomes the new truth.
>
> - **R14.4** `schema_v0.2.1.sql` is the **initial** migration. Alembic's first
>   revision stamps that state; it does not recreate it from models.
> - **R14.5** SQLAlchemy models are written to **match** the frozen schema.
>   Where a model and the schema disagree, the schema is right and the model is
>   a defect.
> - **R14.6** Autogenerated migrations are reviewed as proposed *changes to a
>   frozen baseline*, not as routine output. A migration altering anything in
>   `schema_v0.2.1.sql` requires the same approval path as a schema change, and
>   CI still verifies the frozen digests (`TECHNICAL_BASELINE_FROZEN.md`).
> - **R14.7** The 70-assertion gate suite keeps running against the frozen SQL,
>   not against models. It is the independent check that the ORM has not
>   drifted.

The rules name `v0.2.1` because RFC-001 was written against that package. They
apply to the current frozen baseline, `schema_v0.2.3.sql`, which superseded it
through the approval path R14.6 describes.

## 3. The limits of each guarantee

This section exists because the request was specific: a comparison of catalog
object **counts** is evidence about counts, and is not by itself proof that
every object definition matches. That is correct, and it was true of the
implementation as committed in `779417b`. Two things follow.

### 3.1 What the count comparison does and does not establish

`test_the_migrated_catalog_matches_the_static_audit` compares five numbers —
48 tables, 54 enum types, 17 functions, 37 triggers, 131 foreign keys — from
the migrated database against `STATIC_AUDIT_RESULTS_v0.2.3.json`, which
derives them by parsing the SQL text.

- **It does establish** that two independent derivations agree, so a migration
  that applied a truncated file, or died partway, is caught.
- **It does not establish** that the objects are the *same* objects. Forty-eight
  tables with the wrong columns is still forty-eight tables.

### 3.2 What was added in response

A structural fingerprint, `db/dev/baseline_fingerprint.py`, and a test that
compares a migrated database against one built by applying the frozen SQL
directly. Committed **after** `779417b`.

**Covered**, as normalised text straight from the catalog:

| Object | Source | So a change to… is caught |
|---|---|---|
| columns | `information_schema.columns` | name, position, type, nullability, default |
| constraints | `pg_get_constraintdef` | check expressions, FK targets, delete rules |
| indexes | `pg_get_indexdef` | columns, uniqueness, method, predicates |
| triggers | `pg_get_triggerdef` | timing, events, the function called |
| functions | `pg_get_functiondef` | **the body** — so a rewritten trigger implementation is caught |
| enums | `pg_enum` | labels and their order |

`test_the_fingerprint_notices_a_changed_function_body` proves the last row
empirically by replacing a function body and asserting the fingerprint moves.

**Not covered**, named rather than implied:

- row data of any kind, including the master seed and `schema_metadata`;
- privileges, ownership, row-level security, tablespaces;
- comments, and the physical ordering of anything;
- `alembic_version` itself, excluded deliberately (§3.4);
- **behaviour.** Two structurally identical schemas can still behave
  differently under concurrency or data. Behaviour is the 70-assertion gate's
  job, run against the frozen SQL, which is exactly R14.7.

So the honest claim is: *the same tables, columns, types, constraints,
indexes, triggers and function bodies, as PostgreSQL reports them.* Not
"the databases are interchangeable".

### 3.3 How a stamp of a non-matching database is prevented

The question was well aimed: as committed in `779417b`, **it was not**.
`reset_db.sh` ran `alembic stamp head`, and `alembic stamp` writes a version
row and verifies nothing. A stamp asserts "this database already contains
revision 0001"; a false assertion is invisible until a later migration
half-applies to a structure the history only claims it has.

Closed by `db/dev/stamp_baseline.py`, which `reset_db.sh` now calls instead:

1. reads the target's structural fingerprint;
2. builds a throwaway reference database from the frozen SQL and fingerprints
   it;
3. **refuses (exit 2) unless they are identical**, printing the first
   differences so the refusal is actionable;
4. refuses (exit 3) if the target is already stamped at a *different*
   revision, rather than overwriting the history;
5. only then stamps.

Evidence: `test_stamping_a_database_that_is_not_the_baseline_is_refused`
(builds a database with a single wrong table, asserts exit 2 **and that no
version row was written**), `test_stamping_the_real_baseline_succeeds` (the
guard must not refuse the case it exists to allow), and
`test_the_dev_reset_script_stamps_through_the_guard`, which parses the script's
command lines — comments stripped — and fails on any bare `stamp`. That last
test was itself checked by reverting the script to `alembic stamp head` and
confirming it fails.

**Residual limit, stated:** the guard binds `reset_db.sh` and anything using
`stamp_baseline.py`. A developer who runs `alembic stamp head` by hand still
bypasses it. Nothing in Alembic can prevent that; what is prevented is the
project's own tooling doing it silently.

### 3.4 A defect the fingerprint found immediately

The frozen schema sets `search_path = turab, public`. Alembic's version table
therefore landed in **different schemas depending on how the database was
built**: `public` when created by `upgrade head` on an empty database (before
the schema exists), and `turab` when created by `stamp` on an already-built
one. The same database would keep its history in a different place depending
on its history.

Found by the first run of the fingerprint comparison, which reported
`alembic_version` as present in `turab` on one side and absent on the other.
Fixed by pinning `version_table_schema="public"` in `env.py`, and pinned by
`test_the_version_table_is_pinned_to_public`.

This is offered as evidence for the point the request made: the count
comparison had passed on this database, and could not have surfaced it.

## 5. Verification method note

Where this pack says a test "catches" something, that was checked by causing
the failure, not inferred. Specifically: the frozen file was tampered with,
the stamp was removed from `reset_db.sh`, `reset_db.sh` was reverted to a bare
`alembic stamp head`, a function body was rewritten, and a database with one
wrong table was offered to the stamp guard. Each produced the expected
failure, and each change was reverted.
